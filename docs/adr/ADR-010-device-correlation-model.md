# ADR 010: Device Correlation Model (Phase 1D)

## Status

Accepted

## Context

Phase 1C provides raw, ephemeral `DeviceObservation` records generated by network discovery protocols like ARP. These observations tell us "MAC X was seen at IP Y at Time Z". However, multiple observations across time and interfaces often refer to the same logical device presence on the local network. 

We need a structured way to correlate these ephemeral observations into a stable domain representation (`DeviceRecord`) to evaluate a device's current presence without asserting false cryptographic trust.

## Decisions

### 1. Observational Correlation vs. Cryptographic Identity

**Decision**: A Phase 1D `DeviceRecord` is an observational correlation record, not a trusted identity.

We explicitly separate Layer 2 correlation from cryptographic trust. MAC addresses are used as correlation evidence, but they are not the device's true identity. No path in Phase 1D marks a `DeviceRecord` as trusted, enrolled, or cryptographically verified.

### 2. Opaque Device ID

**Decision**: The `device_id` is an opaque implementation identifier generated dynamically (e.g., via `uuid4`), rather than mathematically derived from the MAC address.

**Rationale**: 
* Deriving the ID mathematically from a MAC address via UUIDv5 would embed the false assumption that MAC == Semantic Identity into our architecture.
* Given MAC randomization and spoofing, relying purely on the MAC for a persistent cryptographic key surrogate would cause downstream architectural flaws. 
* By using an opaque ID, the correlation engine treats MACs simply as evidence mapped to the current opaque session record.

### 3. Scope-Bound Correlation

**Decision**: Correlation is strictly constrained to a specific `NetworkScope`.

**Rationale**:
Observations of the same MAC address across two completely different network scopes (e.g., a home network and a generic corporate network) cannot be mathematically proven to be the same physical device simply due to MAC collisions or randomized generic MACs. Therefore, identical MACs across different `NetworkScope` boundaries will not automatically correlate.

### 4. Conflict Semantics

**Decision**: Observation conflicts (e.g., IP collisions) are preserved explicitly rather than silently overwriting records.

**Rationale**:
If IP 192.168.1.42 is claimed by both MAC A and MAC B in the same scan, throwing one away loses critical security observability. Both MACs will receive separate `DeviceRecord`s, and an `ObservationConflict` of type `IP_COLLISION` will be attached to both records.

### 5. Presence State

**Decision**: The state of a device in Phase 1D memory is either `PRESENT` (observed in the most recent scan context) or `UNSEEN` (known to the session memory but not observed in the most recent scan context).

**Rationale**:
Phase 1D operates purely in-memory and passively observes the network. We cannot prove a device is permanently `ABSENT` or `OFFLINE` just because one scan missed it. `UNSEEN` accurately describes our lack of current observational evidence.

### 6. Ephemeral Memory Boundary

**Decision**: Phase 1D correlation state is session-scoped and ephemeral. Durable retention and pruning semantics are deferred to Phase 1E.

**Rationale**: 
Introducing SQLite or persistent repositories now would violate the roadmap structure and blur the line between real-time observation (Phase 1) and historical lifecycle tracking (Phase 1E).

## Consequences

* MAC randomization remains an accepted limitation of Phase 1D correlation. Devices rotating their MACs will appear as new observational records. Phase 2 introduces an independent cryptographic trust mechanism that solves this.
* An injected ID factory must be provided to the `ObservationCorrelator` for deterministic unit testing.
* Memory usage will grow proportionally to the number of distinct MACs seen during the lifetime of the correlator instance, which is acceptable given the expected /16 maximum scope size and ephemeral application lifecycle.
